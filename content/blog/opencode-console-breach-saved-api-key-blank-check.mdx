On the night of October 16, somebody broke into the OpenCode Console and grabbed the API keys that users had stored there — OpenAI, Anthropic, Google.

Only 1.4 percent of Console users had linked external provider keys. But for those users, every linked key was exposed. The keys were put to work before anyone noticed. Users woke up to bills ranging from a few hundred dollars to $1,700 in charges they never authorized.

OpenCode emailed affected users on the morning of October 17 and posted publicly the same day. But what the breach exposed is older and uglier than any single startup's security posture: the entire way we handle API keys for AI services is fundamentally broken.

## The OpenCode Console Breach: What Happened

OpenCode is an open-source AI coding agent — a developer tool that calls large language models to write and edit code. It ships in two forms: a local CLI that runs on your machine, and a hosted Console where you can use it through the browser.

The Console let users save their own provider API keys — for OpenAI, Anthropic, and Google — so they would persist across sessions. On the night of October 16, an attacker compromised the Console and exfiltrated those stored credentials.

OpenCode co-founder Dax Raad disclosed on X that the breach affected approximately 1.4 percent of Console users — specifically those who had linked external API provider keys.

The earliest possible exposure window was October 17, 00:30 UTC, according to BleepingComputer's timeline. By the time OpenCode detected the intrusion and began notifying users, the stolen keys had already been put to work.

<Callout type="tip">
If you ever stored an API key in OpenCode Console, revoke it immediately at your provider — even if you removed it from Console weeks ago. Removing a key from a third-party tool does not revoke it at the provider.
</Callout>

## The Distillation Theory

OpenCode called this "a large-scale distillation attack." The claim: the stolen keys were not used to run up credits for random compute. They were used to systematically query frontier models and capture their outputs — effectively stealing the intelligence of those models to train cheaper alternatives.

This is not a hypothetical threat. Just four days before the breach, Anthropic published a detailed blog post on its anti-distillation defenses, disclosing that its protections had reduced the data adversaries could harvest by 90 to 99 percent. In that same post, Anthropic named Zhipu, a Chinese AI company, as having distilled models from US providers. Zhipu's GLM-5.3-Flash was released on the same night as the OpenCode breach.

The timing is hard to ignore. But it is also worth asking whether the attackers were after something simpler: free compute. Running inference through stolen keys is cheaper than paying for it. The distinction matters less than you might think — whether the attacker was distilling a model or just mining tokens, the bill lands on the same credit card.

## What It Cost Real People

The damage was personal and immediate:

- **Colin Parsons** reported $281 in unauthorized OpenAI charges, plus another $168 on Anthropic — nearly $450 gone before he noticed.
- **Preston Zeller** posted a $1,700 bill.
- Multiple Reddit users reported charges in the $400 range, with one user in Europe seeing 200 EUR drained.

Google went further than blocking keys. It suspended entire projects for what it classified as "abusive activity" — meaning some users temporarily lost access to their own legitimate work, not just the compromised keys.

Dax Raad later posted: "My personal accounts are being attacked now too." According to TechCrunch, the attackers continued probing OpenCode's systems for over 48 hours after the initial breach.

<Callout type="info">
OpenAI worked with OpenCode to refund affected users. Anthropic and Google blocked the compromised keys.
</Callout>

## Why API Keys Are Bearer Credentials — and Why That Matters

This breach was possible because API keys are bearer credentials. Whoever holds the key is the key.

If you paste your OpenAI key into a third-party tool and that tool gets breached, the attacker is indistinguishable from you as far as OpenAI's servers are concerned. The key does not know who is using it. It does not care.

This is not unique to OpenCode. Any hosted tool that asks you to "bring your own key" and stores it server-side has the same structural vulnerability. Every copy of a key is another place it can leak from.

The difference between OpenCode's local CLI and its hosted Console is instructive. Dax Raad stressed that local keys "never come to us." If you run OpenCode locally, your key stays on your machine. If you use the Console, your key lives on someone else's server — and you are trusting that server's security with a credential that has no way to know if it has been compromised until the bill arrives.

## How the Providers Responded — and Where They Hit a Wall

The major providers responded fast:

- **Anthropic** detected and blocked the compromised keys.
- **Google** suspended projects showing abusive activity patterns.
- **OpenAI** worked with OpenCode to refund affected accounts and granted access to its Daybreak Blue security program so OpenCode could analyze the attack.

But an uncomfortable truth emerged during the investigation: when OpenCode tried to use AI models to analyze the malicious code patterns from the attack, the models' safety filters blocked them. The guardrails designed to prevent misuse also prevented defensive analysis. David Sacks commented on this asymmetry — the safety mechanisms that slow down defenders do nothing to stop attackers already operating outside the rules.

That is the paradox of AI security in 2026. The tools we need to defend against AI-powered attacks are hamstrung by the same policies that the attackers ignore.

## Why Stolen Keys Are Worth More Than Free Compute

Distilling a frontier model — running massive volumes of queries against it and training a smaller model on the outputs — is the fastest shortcut in AI. Anthropic's October 12 blog post laid out the enforcement challenge in unusual detail:

- Distillers operate through networks of fraudulent accounts using stolen payment details.
- They use automated systems to generate large volumes of queries designed to extract maximum training signal.

But a real customer's compromised API key is the one thing a distiller cannot fake. It comes pre-authenticated. It has a legitimate payment method attached. It bypasses every anti-fraud check designed to catch synthetic accounts. A stolen key is not just access — it is a disguise.

<Callout type="warning">
According to GitGuardian's 2025 report, 28.6 million new secrets were exposed on GitHub in 2025 alone — and 70 percent of secrets leaked in 2022 were still active when later checked. The API key problem is not getting better. It is compounding.
</Callout>

## What Local-First Gets Right

The breach drew a sharp line between two architectures.

**Hosted tools** (like OpenCode Console) store your keys on their servers. This is convenient — you sign in from any browser and your keys are there. But it means your security depends on theirs. One breach, and every key they store is compromised simultaneously.

**Local-first tools** (like the OpenCode CLI, or any tool that reads keys from your machine's environment variables) never transmit your key. The attack surface is your own machine, which you control. A breach at the tool vendor does not expose your credentials because the vendor never had them.

This is not a theoretical distinction. As Dax Raad noted, local CLI users were completely unaffected — the 1.4 percent who were hit all used the hosted Console.

The tradeoff is real — local-first means you cannot seamlessly switch devices, and you have to manage your own key storage. But after October 16, that tradeoff looks different than it did before.

## How to Protect Your AI API Keys After OpenCode

If you use any AI coding tool with provider API keys, here is the minimum:

**1. Revoke and rotate every key you have ever pasted into a third-party tool.** Not just OpenCode. Any tool. Go to your provider dashboards — OpenAI, Anthropic, Google — and generate new keys. Delete the old ones. Do it today.

**2. Set spend limits.** Most major providers offer them. Preston Zeller's $1,700 bill is a case study in what happens without one. Even a modest daily cap would have limited the damage.

**3. One key per tool.** Do not reuse the same key across multiple services. If one tool gets breached, only that key is compromised. This is basic credential hygiene, and almost nobody does it.

**4. Use a secrets manager.** Environment variables are better than pasting keys into web forms. A proper secrets manager — 1Password, HashiCorp Vault, AWS Secrets Manager — is better still. The key should never exist in plaintext on a server you do not control.

**5. Rotate on a schedule.** The industry recommendation is every 30 to 90 days. The GitGuardian data on secrets persisting for years suggests most people never rotate at all.

**6. Prefer local-first tools when possible.** If a tool offers both a hosted and local version, use the local version for key storage. The convenience of hosted keys is not worth the risk.

## What the OpenCode Breach Means for AI Security

The OpenCode breach is a preview of a much larger problem.

AI agents are proliferating. Every major tech company is shipping agents that need API keys to function. Those keys are being stored in more places, by more tools, with more attack surface than ever before. And the incentive to steal them is growing — not just for free compute, but for distillation, for competitive intelligence, for building the next generation of models on someone else's research budget.

Dax Raad put it plainly: "It's a whole new world with AI-powered hacking. We basically need agents going 24/7 because that's what they have."

The attackers are automated. The defense cannot be manual.

The API key as we know it — a static string, a bearer token, a blank check — was designed for a world where the main threat was accidental exposure. It was not designed for a world where sophisticated adversaries run automated agents around the clock, looking for exactly these credentials.

Something has to change. Whether that is short-lived tokens, hardware-bound credentials, or identity-aware access policies, the current model of "paste your key and hope" is not going to survive contact with the threat landscape of 2027.

Until then, treat every saved API key like what it is: a signed blank check, sitting in someone else's filing cabinet, waiting for the lock to break.
