On July 18, Peter Steinberger posted twelve words that racked up 2.9 million views: "Are we still talking loops or did we shift to graphs yet?"

A corner of the internet that had just finished learning loops declared them old news overnight. Engineers pushed back quickly, pointing out this is a decades-old idea wearing a new name. Both sides were right, and that tension is exactly why this matters.

If you read my [loops article](/blog/stop-prompting-agents-start-designing-loops), you already have the foundation. A loop is one agent improving one thing on repeat: observe, plan, act, verify, go again. That was the skill of last month. What everyone is moving to now is not a better loop. It is a graph of loops — a network where cycles watch and correct each other instead of one agent chasing one number alone.

## What a Graph Actually Is

A graph is just a plan for your AI work, drawn out so you can see it. It answers two questions: which jobs need to happen, and which job has to wait for which.

There are only two parts.

**A node** is one job. One agent doing one task, with one thing going in and one thing coming out. Researching a competitor. Writing a draft. Checking a claim.

**An edge** is a dependency. It means one job needs what another job produced, so it has to wait for it. The edge only counts when something real actually passes along it.

Nodes do the thinking. Edges carry the results. That is the entire vocabulary.

<Callout type="info">
**The relationship is simple:** a loop is just a special case of a graph — a single node with an edge back to itself. If you can design one loop, you already understand the building block. A graph is what happens when you wire several of them together.
</Callout>

## Why Your Chain Is the Bottleneck, Not the Model

When you write an agent workflow as "do A, then B, then C, then D," you have technically drawn a graph. It is just the worst possible one: a straight chain where every node has one arrow in and one arrow out.

It runs correctly. It also runs slowly and breaks easily, because a chain has no redundancy. If step C stalls, step D never happens, and A's work is trapped upstream with nowhere to go.

The numbers confirm this. Research from Zylos AI found that agent systems using parallel concurrency deliver consistent 1.8x to 3.7x wall-clock speedups over sequential execution. The LLMCompiler framework measured up to 3.7x speedup and 6x cost reduction on parallelizable workflows. A March 2026 approach called PASTE reported a 48.5% reduction in average task completion time.

These are not marginal gains. A workflow with 40 sequential steps has 40 points of failure and the latency of all 40 added together. The same 40 jobs drawn as a graph, with fake edges removed, finish at the speed of your slowest real dependency chain — not the sum of everything.

The model was never the bottleneck. The line you drew was.

## The Test That Finds the Fake Edges

Here is the most immediately useful skill in graph engineering: look at any workflow you run today and walk it step by step. At each step, ask one question.

**Does this step actually need the result of the one before it?**

If yes, the edge is real. Keep the order. If no, there is no edge, and the wait is wasted. Those two jobs can run at the same time.

Take a simple one: "review file A for bugs, then review file B for bugs." It reads like a sequence, but the check on file B never looks at what file A returned. They only run one after another because that is the order you typed them in. Run them side by side and the whole thing finishes in the time of the slower single file, not the two added together.

You will find fake edges like this in almost any workflow you draw. Every one of them is free time you are throwing away.

## The Node Contract: What Makes a Node Wire-able

The thing that makes a node actually usable in a graph is a contract. One bounded job. A defined input. A defined output.

```text
NODE CONTRACT
JOB:    research one competitor's pricing (one job, nothing else)
IN:     { competitor: "name", url: "https://..." }
OUT:    { price: number, plan: string, source: url, date: "YYYY-MM-DD" }
SCHEMA: enforced — if the agent returns free text, it is rejected and retried
```

A node whose output is a wall of free text is a node only a human can read. A node with a fixed output shape is one the next node can consume without guessing, and that is the whole point. Structured output is what makes one node's work machine-readable to the next, removing the need for a human translator in the middle.

This matters because the contracts are where most multi-agent systems actually break. The MAST study from UC Berkeley and CMU (Cemri et al., 2025) analyzed over 1,600 execution traces across seven popular agent frameworks and identified 14 distinct failure modes. The largest category — specification and system design issues — accounted for 41.8% of all failures, covering ambiguous role definitions, poor task decomposition, and missing contracts between agents.

<Callout type="warning">
**The compounding problem:** a 4-stage pipeline where each stage has a 30% error rate yields only a 24% end-to-end success rate (0.7⁴). Every node you add without a tight contract multiplies your failure surface. Graphs do not solve this — they expose it, which is why contracts come first.
</Callout>

## The One Pattern That Pays: The Diamond

You do not need a hundred shapes. Watch any serious agent system work and the same picture keeps appearing. The work fans out, several workers dig in parallel, something checks and compresses what they found, and everything merges back into one answer.

That shape is called the diamond, and its formal name is worth remembering: **fan out, reduce, synthesize.**

Fan out to gather breadth. Reduce with plain code to compress it. Synthesize with a final agent to write the answer.

A production study found the fan-out/fan-in pattern reduces wall-clock time by 36 to 50 percent in common content and research workflows.

Here is what a diamond looks like in practice for a competitive analysis:

**Fan out (3 parallel nodes):** Three researcher agents each analyze one competitor's pricing, features, and positioning. They run simultaneously with isolated contexts.

**Reduce (plain code):** A script merges the three structured outputs into a single comparison table. No LLM needed — this is just data shaping.

**Synthesize (1 node):** A writer agent receives the clean comparison table and produces the final brief. It never saw the raw research, only the structured summaries.

Total wall-clock time: the speed of the slowest researcher plus the synthesis step. Compare that to running three researchers sequentially plus synthesis — three times slower for the same result.

## The Four Failures Graphs Are Built to Catch

Carlos E. Perez, writing in the Intuition Machine publication, laid out why single loops eventually break down. His framework applies directly to agent systems:

**Goodhart's Law.** A metric optimized intensely stops measuring what it was supposed to measure. The support bot that "resolves" tickets by deflecting them improves the resolution rate while destroying customer retention. A graph catches this by pairing metrics — resolution rate watched by a renewal-rate loop that flags when the numbers diverge.

**Blindness upward.** A loop cannot question whether its own target is correct. It drives toward whatever reference was set, potentially achieving the wrong goal efficiently. In a graph, slower loops own faster loops' targets. The quarterly strategy loop sets what the daily execution loop optimizes for.

**Conflict.** Independent loops fight when they share systems. A speed-optimization agent undermines a thoroughness agent. A growth agent strains a culture agent. A graph makes these dependencies explicit so conflicts surface before they compound.

**Measurement decay.** Sensors drift. Data pipelines rot. Definitions shift while dashboards stay green. In a graph, audit loops independently verify that numbers still match reality.

## The Framework Landscape Right Now

The first half of 2026 saw a wave of agent framework releases, and the graph-versus-loop debate landed right in the middle of it.

**LangGraph** offers graph-based orchestration with per-node timeouts, conditional edges, and persistent state management. It is used in production by Klarna, Uber, and J.P. Morgan, among others.

**Microsoft merged Semantic Kernel and AutoGen into Microsoft Agent Framework 1.0**, shipping graph-based orchestration with sequential, parallel, conditional, and looping flows via its GraphFlow API.

**The Claude Agent SDK** added hierarchical subagent spawning, implementing an orchestrator-worker pattern where subagents function as graph nodes with scoped tool access and isolated contexts.

**CrewAI 1.14** introduced pluggable memory backends. **Pydantic AI V2** and **LlamaIndex Workflows 1.0** both went stable.

The honest assessment from the AI Builder Club's four-question gut check: if you split contexts into specialized ones, have real fan-out/fan-in, can read control flow as a diagram, and your success criteria actually changed — you have a real graph. If you just renamed your loop, you have a buzzword.

## When to Stay on Loops

Not everything needs a graph. Harrison Chase, the creator of LangChain, said it plainly: "I didn't really know what graph engineering is, and I still don't."

David K, the creator of XState, put it sharper: "We're constantly rediscovering decades-old patterns and repackaging them as innovations."

They are both right, and their skepticism is the most useful filter.

**Stay on a loop when:**
- The task is well-scoped and does not naturally split into specialties
- One capable agent with a strong tool library can handle the full cycle
- You run it once or infrequently
- The overhead of coordination would exceed the time saved by parallelism

**Move to a graph when:**
- One agent's output becomes another agent's input, and they need different tools or contexts
- Work naturally parallelizes across specialized agents
- You need auditable control flow — debugging means reading a routing diagram, not scrolling a transcript
- Multiple automation loops have accumulated without design and are starting to conflict

The mistake is treating graphs as a replacement for loops. A loop is a node. A graph is how you connect them. You need both.

<Callout type="tip">
**The cost tradeoff is real.** Anthropic's own engineering data shows multi-agent systems consume roughly 15x the tokens of a single chat interaction. Graphs trade tokens for speed and quality — a trade worth making only when work genuinely separates into parallel specialties. If your graph is just a fancy way to run tasks sequentially, you are paying 15x for nothing.
</Callout>

## Getting Started: Your First Graph

You already have a loop from the last article. Here is how to turn it into a graph.

**Step 1 — Draw it.** Take your existing loop and write out every step. For each arrow between steps, ask the fake-edge question. Cut the ones that carry no data.

**Step 2 — Define contracts.** For every node, write the input schema and output schema. If you cannot define the output shape, the node is too vague. Split it or constrain it.

**Step 3 — Find the diamond.** Look for the place where work can fan out. Research tasks, file reviews, data gathering — anything where separate contexts improve quality. That is your first parallel layer.

**Step 4 — Wire it.** Use whatever tool fits your stack. LangGraph if you want full graph orchestration. Claude Code subagents if you are already in that ecosystem — start with interactive subagent definitions, add hooks for deterministic edges, and lift stable patterns into the Agent SDK. Microsoft Agent Framework if you are in the Azure ecosystem.

**Step 5 — Measure.** Compare wall-clock time and output quality against your sequential version. If the graph is not measurably faster or better, simplify it back down.

## The Pattern That Has Run Critical Systems for Thirty Years

The engineers who pushed back on the hype were right about the most important thing: graph orchestration is not new. Control theory, state machines, DAG scheduling, and process pipelines have used these patterns for decades. What changed is not the pattern — it is what sits inside the nodes. An LLM agent that can read, reason, and write code is a fundamentally different kind of worker than a cron job or a bash script.

The fact that graphs are a proven, boring, well-understood architecture is exactly why you should trust them with your work. The exciting part is not the shape. The exciting part is that the nodes can think now.

Your loops still run inside every node. The graph just makes sure they are not running alone.
