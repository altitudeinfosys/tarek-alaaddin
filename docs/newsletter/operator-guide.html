1 · Architecture at a glance

Short answer to “do we need the DB?” Yes — your Neon Postgres DB is the source of truth for who your subscribers are, their topic preferences, their unsubscribe tokens, and which post has already been emailed to which subscriber. Resend is the sending transport, plus a dashboard mirror for visibility.

The two systems and their roles

SystemWhat it stores / doesWhy we need it
Neon Postgres
source of truth		 subscribers — email, name, status, topic prefs, unsubscribe token
sends — one row per post-broadcast
sent_to — join table, which subs got which send (idempotency) 		Resend doesn't natively model your topic preferences, your idempotent “one post = one broadcast” semantics, or your per-subscriber unsubscribe tokens. The DB gives you ownership of your list, no vendor lock-in, and the cron reads from here to decide who to email.
Resend
transport + mirror		 Sends every email (welcome + newsletter broadcasts)
“General” audience — mirror of your DB subscribers
Email logs, open/click/bounce metrics 		You get delivery status and a dashboard without building them. The audience mirror means you can scroll a list and see counts without opening a terminal. Your Resend account is shared with your other apps, so Emails and Metrics include their traffic unless you filter.

Which should you look at?

For "who's on my list / who just signed up" → the admin dashboard or Resend's audience page work equally (they're in sync).

For "did my blog post get delivered or bounce?" → Resend Emails, searching for the post title. Opens and clicks need tracking turned on first (see section 3).

For data exports or anything scripted → the admin dashboard's JSON API (pulls from the DB).

2 · View subscribers

Easiest Your admin dashboard

Open in a browser:

https://www.tarekalaaddin.com/admin/newsletter?key=<CRON_SECRET>

Shows total/active/inactive counts, a Recent sends table, and the full subscriber list with email, name, status, and signup date.

Get the key: vercel env pull .env.local → grep for CRON_SECRET.

Resend audience page

Open in a browser:

resend.com/audience

Mirror of your DB. Same count, same emails, same unsubscribed state. Updated automatically on every new signup and unsubscribe.

For scripting / exports — JSON API

curl -sS "https://www.tarekalaaddin.com/api/newsletter/subscribers" \
  -H "Authorization: Bearer $CRON_SECRET" | jq

Export to CSV for migration or reporting:

curl -sS "https://www.tarekalaaddin.com/api/newsletter/subscribers" \
  -H "Authorization: Bearer $CRON_SECRET" \
  | jq -r '.subscribers[] | [.email, .first_name, .status, .source, .subscribed_at] | @csv' \
  > subscribers-$(date +%Y-%m-%d).csv

3 · View send history & email metrics

The Recent Sends table in your admin dashboard

The admin dashboard's “Recent sends” table shows post title, send time, and recipient count for every post that actually went out.

In Resend directly

WhereWhat you see
resend.com/emails Every email on your account, across all your apps, with delivery status. Use the search box with a post's title to find its sends.
resend.com/metrics Deliverability, bounce, and complaint rates. Change “All domains” to tarekalaaddin.com so your other apps aren't counted.
resend.com/logs Low-level API request log, useful for debugging a failed send.

Open and click rates are not being collected

As of 2026-11-06, open and click tracking are off for tarekalaaddin.com in Resend, so those charts have no newsletter data. To enable them, open Resend → Domains → tarekalaaddin.com → Configuration → Enable tracking metrics. Resend asks for a custom tracking subdomain, which means adding a DNS record in Cloudflare. Past sends can't be backfilled.

About the tags

Cron emails carry the tags kind=newsletter and slug=<post-slug>. Resend's Emails page has no visible tag filter, so they're useful for webhooks and API use, not for browsing. Welcome emails are untagged.

4 · When emails are sent (and how to force one)

Automatic flow — happens without you

1

You push a new blog post to main

MDX file in content/blog/ with date: on or after NEWSLETTER_CUTOFF_DATE (currently 2026-04-18) and published: true (default).

2

Vercel builds and deploys to production

The site publishes posts often, so subscribers can get an email on most days: one per new post, not a weekly digest.

3

Next day at 14:00 UTC (~9 AM Central, ±59min on Hobby)

Vercel Cron hits /api/cron/newsletter with the authenticated secret.

4

The cron finds new posts, queries active subscribers, sends via Resend batch API

Idempotent — if a partial send fails, re-running picks up only the subscribers who didn't receive the email. Each email tagged kind=newsletter and slug=<post-slug>.

Force-send a specific post right now (bypass the daily schedule)

curl -sS -X POST "https://www.tarekalaaddin.com/api/cron/newsletter" \
  -H "Authorization: Bearer $CRON_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"slug": "your-post-slug"}' | python3 -m json.tool

Still idempotent: if a subscriber already received this post, they won't get it again. Use this when you want to publish a post and immediately email it out.

Preview what the cron would send (dry-run, no email goes out)

curl -sS -X POST "https://www.tarekalaaddin.com/api/cron/newsletter" \
  -H "Authorization: Bearer $CRON_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"dryRun": true}' | python3 -m json.tool

Returns the list of candidate posts and how many recipients each would reach.

5 · Common tasks

I want to…Do this
Publish a post without emailing anyone Three options: set published: false in frontmatter (also hides from blog) · set date: earlier than NEWSLETTER_CUTOFF_DATE · preemptively insert a row into sends for that slug before deploying.
Pause all newsletter sends temporarily Delete NEWSLETTER_CUTOFF_DATE from Vercel env. The cron will refuse to run. Re-add it to resume.
Change the daily send time Edit vercel.json → crons[0].schedule (currently "0 14 * * *" = 14:00 UTC) and push.
Manually unsubscribe someone See docs/NEWSLETTER-RUNBOOK.md §8 — direct SQL update. Also unsubscribe them in Resend → Audience, because a direct SQL change doesn't sync.
Re-send a post to everyone (danger) See docs/NEWSLETTER-RUNBOOK.md §7 — delete sent_to rows for that send, then force-send.
Test email delivery without affecting real subscribers Subscribe yourname+test@... via the signup form, then force-send to a slug. Delete the test row after.
Re-backfill the Resend audience (if it falls out of sync) node --env-file=.env.local scripts/sync-audience-backfill.mjs — idempotent, safe to re-run.

6 · Env vars checklist

Set in Vercel → Settings → Environment Variables. After adding, redeploy.

RESEND_API_KEY
Resend Pro key — powers all sending and audience sync
DATABASE_URL
Neon Postgres connection string — source of truth
CRON_SECRET
Bearer token for cron, admin dashboard, subscribers API, sends API
NEWSLETTER_CUTOFF_DATE
ISO date, posts before this never email. Delete to pause.
TURNSTILE_SECRET_KEY
Server-side Turnstile verification for /subscribe
NEXT_PUBLIC_TURNSTILE_SITE_KEY
Client widget key
NEXT_PUBLIC_SITE_URL
Canonical URL used in email links
RESEND_AUDIENCE_ID (optional)
Defaults to the existing “General” audience
RESEND_SENDER (optional)
From-address; defaults to newsletter@tarekalaaddin.com
RESEND_REPLY_TO (optional)
Reply-to; defaults to tarek@tarekalaaddin.com

Quick check what's set in production (auth-gated):

curl -s "https://www.tarekalaaddin.com/api/health" -H "Authorization: Bearer $CRON_SECRET" | python3 -m json.tool

7 · Troubleshooting

SymptomLikely cause & fix
“Cron ran but no email arrived” Hit the dry-run endpoint — is processed > 0? Is the post's row already in the sends table (already sent)? Any active subscribers? Check Resend Logs for bounce/failure.
Cron returns 500: NEWSLETTER_CUTOFF_DATE is not set Env var got unset. Re-add in Vercel. Redeploy.
Admin dashboard shows 404 or Unauthorized CRON_SECRET query param doesn't match the Vercel env value. Run vercel env pull .env.local to refresh.
Dry-run shows 0 processed but I just published Is it merged to main? Has Vercel deployed? Is date: in frontmatter on or after cutoff? Is published: true? Is there already a sends row (would skip)?
Partial send — some batches failed The cron is idempotent — re-run the force-send for the same slug. It skips subscribers who already got the email and retries the rest.
Resend audience count doesn't match DB Re-run the backfill script. node --env-file=.env.local scripts/sync-audience-backfill.mjs --dry-run to see the counts, then without --dry-run to sync.
Welcome email didn't arrive after signup Check Resend Logs for that recipient. Common causes: the address doesn't exist (bounced), the mail provider is rate-limiting, or RESEND_API_KEY isn't set in prod. Check /api/health with auth.
